\begin{slide}{Vibe Coding}

\begin{itemize}

\item Vibe coding typically looks like the following:

\begin{itemize}

\item Write a prompt, e.g. ``Build an app that does X.''

\item LLM generates some code

\item User tries it out, notices some things that do not work

\item User writes another prompt requesting changes

\item LLM changes code

\item Wash, rinse, repeat

\end{itemize}
  

\end{itemize}
  
\end{slide}



\begin{slide}{Agentic Coding}

\begin{itemize}

\item Gives an LLM specific software development tasks,
  such as:

\begin{itemize}

\item Specify goal

\item Devise a plan: break up overall task into subtasks

\item Generate code

\item Validate code (for example by running tests)

\item Revise plan or implementation

\item Repeat until satisfied

\end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Vibe-Coding vs. Agentic Coding}

\begin{itemize}

\item Vibe coding isn't always bad, and agentic coding isn't always the right approach

\item Vibe coding:

  \begin{itemize}
    
  \item makes sense for rapid prototyping
    
  \item is for quickly trying out things
    
  \end{itemize}
    
\item Agentic coding

  \begin{itemize}
    
  \item is a thorough process
    
  \item creates reliable code
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{What Can Go Wrong?}

\begin{itemize}

\item AI gets stuck in infinite loops

\item Delivers incorrect solutions confidently

\item Cheats: optimize for validation such as benchmarks
  
\item Implements what you said, not what you meant

\begin{itemize}

\item General problem, existed before AI

\end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Summary}

\begin{itemize}

\item Then: translate ideas into code (programming)

\item Now: translate ideas into prompts (vibe-coding)

\item Then: (systematically) applying principles and methods to create
  reliable software (software engineering)

\item Now: give an AI (software-engineering) goals and constraints to create
  software (agentic coding)

\item Important question: how much of the software-engineering process can be
  delegated?
  
  
\end{itemize}
  
\end{slide}

\begin{slide}{Introduction}

\begin{itemize}

\item The aim is not to give a detailed technical description of LLMs (and the
  agents utilizing them)

\begin{itemize}

\item You don't need to build an LLM or agent,

\item but to understand how they react to your input

\end{itemize}

\item In a nutshell, an LLM is autocomplete on steroids

\begin{itemize}

\item It doesn't look up an answer

\item It generates its response incrementally, depending on the context and
  the data it was trained on

\end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Autocomplete vs. LLM}

\begin{itemize}

\item If you type a message on your phone, it tries to predict how the message
  continues

\begin{itemize}
  
\item Uses a dictionary and probabilities for continuations

\end{itemize}
  
\item An LLM works at a different scale

\begin{itemize}

\item Instead of a dictionary, uses a neural network with billions or
  trillions of parameters

  \begin{itemize}

    \item Not just larger, also tries to generalize
    
  \end{itemize}
  
\item Utilizes a much larger context (thousands of words)

\item Depending on the setting, it may not always return the most probable answer
  
\end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Tokens}

\begin{itemize}

\item An LLM doesn't work with words, uses tokens instead

\item We only give a brief introduction to tokens

\item What do tokens look like?
  
\begin{itemize}

\item (Short) words, e.g. \textit{house}

\item Parts of words, e.g. \textit{un con stitu tion al}

\item Punctuation, whitespace, emojis
  
\end{itemize}

\item Tokens are used

\begin{itemize}
  
\item to avoid vocabulary explosion
\item identify new words
\item describe concepts independent of language

\end{itemize}

\end{itemize}
  
\end{slide}




\begin{slide}{Generating an Answer}

\begin{itemize}

\item Context: current prompt and previous input/output

\item An LLM then generates a plausible continuation: \\
context $\rightarrow$ next token $\rightarrow$ next token $\rightarrow$ next token

\item A generated token is added to the context

\item The \emph{context window} plays a crucial role
  
\end{itemize}

\vspace*{-.3cm}
\begin{center}
\includegraphics[height=4.5cm]{pics/contextwindowparadox.eps}
\end{center}


\end{slide}




\begin{slide}{Context Window}

\begin{itemize}

\item Process is driven by the content of the context window

  \begin{itemize}
  
  \item This window is not infinitely large
    
  \item Higher recall at edges (beginning/end)

\end{itemize}
  
\item Some similarity to our brain's working memory

  \begin{itemize}

  \item Can hold seven chunks of information (+/-2)

  \item Serial position effect (easier to remember start/end)
    
  \end{itemize}

\end{itemize}

\vspace*{.5cm}

\begin{itemize}
  
\item Takeaway: if we want good results, we have to provide the right context
  
\end{itemize}
  
\end{slide}




\begin{slide}{From Chatbot to Agent}

\begin{itemize}

\item We don't want to use the LLM in the following way: \\
  prompt $\rightarrow$ answer

\item First of all, there's an issue with reliability

  \begin{itemize}

  \item LLMs can be confidently incorrect
  
  \end{itemize}

\item Given a prompt (and all their learned patterns), an LLM gives plausible
  answers

  \begin{itemize}

  \item LLMs do not know what the outside world looks like
  
  \end{itemize}

\item We want evidence for correctness

  \begin{itemize}

  \item Idea: give LLMs access to tools for checking
  
  \end{itemize}
  
\end{itemize}
  
\end{slide}

\begin{slide}{From Chatbot to Agent (3)}

\begin{itemize}

\item In the context of coding, we provide tools such as

  \begin{itemize}
    
  \item Requirement/specification documents
    
  \item Code files
    
  \item Tests
    
  \item Current repository and history
    
  \item External documentation
    
  \end{itemize}

\item In agentic coding, the LLM itself is not the agent

  \begin{itemize}

  \item The agent is the system driving the above loop and using the LLM
    
  \end{itemize}
  
\end{itemize}

\begin{slide}{A Cautionary Tale}

\begin{itemize}

\item Assume you want to analyze some experimental data

\item You enter the following as a prompt: \\
  ``Write a program that analyzes experimental data.''

\item What do you expect the agent to produce?

\vspace*{.2cm}
\begin{center}

\end{itemize}

\begin{slide}{A Cautionary Tale (2)}

\begin{itemize}

\item To generate sensible code, an agent needs to know:

  \begin{itemize}
    
  \item What kind of experiment?

  \item What do we mean by ``analyze''?

  \item Which questions do we want answered?
    
  \item What does the data look like?

  \item What output do we want?

  \item Who will use the result?

  \item How do we check correctness?
    
  \end{itemize}

\item We need to define a lot of different aspects
  
\end{itemize}
  
\end{slide}




\begin{slide}{Covering Different Aspects}

\begin{itemize}

\item \textbf{Problem}: what is the general goal?

\item \textbf{Requirements}: what should the program do?

\item \textbf{Specification}: how should it do it?

\item \textbf{Constraints}: what must/mustn't it do?

\item \textbf{Acceptance criteria}: how do we check it's correct?

\item \textbf{Examples}: what do concrete use cases look like?

\end{itemize}
  
\end{slide}



\begin{slide}{Back to Our Example}

\begin{itemize}

\item Problem
  
\begin{itemize}

\item Analyze my experimental data

\end{itemize}

\item Requirements
  
\begin{itemize}

\item Load CSV files
\item Calculate summary statistics
\item Identify outliers
\item Produce result file and plots

\end{itemize}
  
\end{itemize}
  
\end{slide}




\begin{slide}{Back to Our Example (2)}

\begin{itemize}

\item Specification

\begin{itemize}

\item For each CSV file
  
\begin{itemize}

\item group measurements by experimental condition
\item compute mean, median and standard deviation
\item identify observations more than 3 standard deviations from the group mean
\item \dots

\end{itemize}

\end{itemize}

\item Constraints

\begin{itemize}

\item For the plots, use matplotlib
\item Don't use Python versions older than 3.14
\item Don't modify the original data files

\end{itemize}

\end{itemize}


\end{slide}




\begin{slide}{Back to Our Example (3)}

\begin{itemize}

\item Acceptance criteria
  
\begin{itemize}

\item A handcrafted example (with known output) produces the same output
\item \texttt{results.csv} has to pass some statistical tests


\end{itemize}

\item Examples
  
\begin{itemize}

\item Provide typical snippets of experimental data
\item Also include some edge cases
  
\end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Resolving Ambiguities}

\begin{itemize}

\item What happens if we don't provide this information?

\item LLMs always give an answer

\item They resolve ambiguities by filling in the gaps

  \begin{itemize}

    \item Based on the most plausible options from training

  \end{itemize}

\item This does not usually get you what you want.
  
\end{itemize}

\begin{slide}{Decomposition}

\begin{itemize}

\item Once the specification is done, ask the following: \\
  Can this be broken down into smaller subtasks?

\item For analyzing experimental data, this could look like

\begin{itemize}

\item Load data (specifying input format + validation)

\item Group observations

\item Calculate statistics

\item Detect outliers

\item Write results

\item Generate plots

\item Decide whether to accept analysis

\end{itemize}
  
\end{itemize}
  
\end{slide}




\begin{slide}{Decomposition (2)}

\begin{itemize}

\item Gives you checkpoints

  \begin{itemize}
    
  \item Instead of producing thousands of lines of code,

  \item implements and verifies one part at a time
    
  \end{itemize}

\item Also helps with resolving ambiguities

\begin{itemize}

\item Can now also be done for one part at a time

\end{itemize}

\item We talk more about decomposition in the next chapter

\end{itemize}
  
\end{slide}

\begin{itemize}

\item Maps nicely onto the loop from the previous chapter:

\begin{itemize}

\item Perceive Goal -- Problem

\item Plan Steps -- Specification

\item Act -- Implement

\item Observe Results -- Check Acceptance Criteria

\end{itemize}

\item If it isn't working, refine specification

\end{itemize}

\begin{slide}{Summary}

\begin{itemize}

\item Agentic coding is not about finding the ``magic'' prompt

\item It's about (systematically) getting rid of ambiguities

  \begin{itemize}
    
  \item If we don't, an LLM will fill gaps on its own
    
  \end{itemize}
  
\item So, if things don't work

  \begin{itemize}
    
  \item Don't ask an agent to fix the code

  \item Instead, go over the specification
    
  \end{itemize}
  
\end{itemize}

\begin{slide}{Architecture vs. Design}

\begin{itemize}

\item Software developers use different terminology when it comes to
  structuring code

  \begin{itemize}
    
  \item Architecture: high-level view of a system's structure
    
  \item Design: more concerned with individual components
    
  \end{itemize}

\item There is no strict boundary between the two

\item We're not going into details here

  \begin{itemize}
    
  \item Important for you: you need to structure the code
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}




\begin{slide}{Modules}

\begin{itemize}

\item In Python, modules structure your code

\item A module is simply a file containing Python code

\item E.g., we could introduce the following structure:
  
\end{itemize}

\vspace*{-.3cm}
\begin{scriptsize}
\dirtree{%
.1 project/.
.2 data/.
.3 \mbox{loader.py}.
.3 \mbox{cleaning.py}.
.2 analysis/.
.3 \mbox{statistics.py}.
.3 \mbox{outliers.py}.
.2 reporting/.
.3 \mbox{results.py}.
.2 visualization/.
.3 \mbox{plot.py}.
.2 \mbox{main.py}.
}
\end{scriptsize}

\end{slide}




\begin{slide}{Modules (2)}

\begin{itemize}

\item It's not about how many files there should be
  
\item In software development, modules are about

  \begin{itemize}

  \item responsibilities

  \item interfaces

  \item dependencies
    
  \end{itemize}

\item In agentic coding, they also set boundaries
  
\end{itemize}
  
\end{slide}



\begin{slide}{Responsibilities}

\begin{itemize}

\item Ideally, a module should perform one specific task

\item Questions to ask yourself are:

  \begin{itemize}
  
  \item Does every module have a clear purpose?

  \item Are any modules doing too many unrelated things?

  \item Are there unnecessary modules?
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Interfaces}

\begin{itemize}

\item The interface defines how the outside world interacts with a module

\item Should not reveal internal implementation details

\item States which services a module provides

\item Questions to ask yourself are:

  \begin{itemize}
  
  \item What does each module expose?

  \item Are the interfaces simple?

  \item How much do modules need to know about each other?
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Dependencies}

\begin{itemize}

\item A module $A$ depends on module $B$ if it relies on the functionality of $B$ to
  work correctly

\item There is also indirect, transitive dependency

\item High dependency makes code hard to change or test independently

  \begin{itemize}
  
  \item Which modules depend on which other modules?

  \item Are there circular dependencies?

  \item Could a change in one modules unnecessarily affect many others?
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}




\begin{slide}{Agent Boundaries}

\begin{itemize}

\item Code structure defines the working environment

\item An agent is able to work locally:

  \begin{itemize}
    
  \item A module's implementation can be changed without affecting the
    environment outside

  \item A good interface tells an agent what it may rely on without looking at
    the inner workings
    
  \end{itemize}
  

\end{itemize}
  
\end{slide}





\begin{slide}{Agent Boundaries (2)}

\begin{itemize}

\item This has an impact on

  \begin{itemize}
    
  \item where an agent searches for making changes

  \item what the agent changes

  \item how much unrelated code it can affect

  \item how easily changes can be reviewed
    
  \end{itemize}

\item You can explicitly tell an agent to make changes to only one module (or
  few modules)

\item Ultimately, this lowers the amount of information needed in the context window
  
\end{itemize}
  
\end{slide}



\begin{slide}{Agent Boundaries (3)}

\begin{itemize}

\item Questions to ask yourself are:

  \begin{itemize}
  
  \item If an agent is told to modify functionality, which file should it look
    at (and is this obvious)?
      
  \item Can it make the change without modifying a number of other modules?

  \item May an agent accidentally cross boundaries?
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Summary}

\begin{itemize}

\item Don't let the agent turn a specification directly into a pile of code.

\item First, decide how to divide the problem into components and decide where
  the boundaries are

\item Then let the agent implement within these boundaries

\item You can let the agent propose a code structure, but you should not
  delegate all decisions to it

\begin{itemize}

\item For larger projects, agents have a tendency to create too many modules

\end{itemize}
  
  
\end{itemize}
  
\end{slide}

\begin{slide}{From Design to Implementation}

\begin{itemize}

\item So far, we have problem $\rightarrow$ specification $\rightarrow$ structuring

\item However, the structure is not an implementation plan

  \begin{itemize}

  \item Don't just tell the agent: now build all this
    
  \end{itemize}

\item Manage the agent via an implementation loop
  
\end{itemize}

\vspace*{.2cm}
\begin{center}
  \includegraphics[width=9cm]{pics/imploop.eps}
\end{center}
\vspace*{.2cm}

\begin{itemize}
  
\item Again, very similar to agentic loop
  
\end{itemize}

\end{slide}



\begin{slide}{Subtasks}

\begin{itemize}

\item Divide implementation into (independent) subtasks

\item Structure should help in this; if it doesn't, you may want to
  reconsider the structure
  
\item Ideally, we have the following:

  \begin{itemize}
    
  \item The goal is clear

  \item The relevant requirements are known
    
  \item The scope is bounded

  \item There is a clear completion criterion that can be inspected and tested
    
  \end{itemize}

\item This is closely related to the specification
  
\end{itemize}
  
\end{slide}





\begin{slide}{Example}

\begin{itemize}

\item Implementing the data loader is a good subtask

  \begin{itemize}
    
  \item Goal: load CSV file from disk into memory 

  \item Requirements: file name and format of input file, we also need
    to know format in main memory

  \item Scope: all we do is load data from disk to memory

  \item Correctness: all data has been correctly loaded
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Planning}

\begin{itemize}

\item LLMs seem to be eager to generate code

\item Tell it not to implement the code yet, but to do some planning first

  \begin{itemize}
    
  \item Many agents have a read-only plan mode (\texttt{/plan})
    
  \end{itemize}

\item In the planning phase, ask the agent to

  \begin{itemize}
    
  \item inspect the relevant code (if there's already code)

  \item explain the proposed approach

  \item identify files that are changed

  \item point out any ambiguities

  \item generate tests to check correctness
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Implementation}

\begin{itemize}

\item Once you're happy with the plan, then you can tell the agent to implement

\item This step does not need any interaction

\item However, you can still follow the output as the agent generates the code

\item You may catch something that looks strange

\end{itemize}
  
\end{slide}



\begin{slide}{Inspecting Changes}

\begin{itemize}

\item Don't trust the explanations of the agent

\item You should run some tests on the code

  \begin{itemize}
    
  \item Tests should be written/generated before the code

  \item As this is an important topic, we provide more details in the
    following chapter
    
  \end{itemize}
  
\item Depending on the outcome, you do different things

\end{itemize}

\begin{slide}{Failing Tests}

\begin{itemize}

\item You need to diagnose the failure

  \begin{itemize}
    
  \item You can ask the agent to help you

    \begin{itemize}
      
    \item Provide details of the test outcome

    \item Ask it determine why it happened
      
    \end{itemize}
    
  \item You can also look at the code changes

    \begin{itemize}
      
    \item Request explanations from the agent

    \end{itemize}
    
  \end{itemize}

\item Tell the agent to fix the code

  \begin{itemize}
    
  \item It should not change the tests
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Succeeding Tests}

\begin{itemize}

\item Even if all tests succeed, it may still be a good idea to look at the
  code yourself

\item First, you have to find the changes

  \begin{itemize}
    
  \item Git has the command \texttt{diff} to show all changes
    
  \item You can also ask the agent to point them out
    
  \end{itemize}

\item Then review them yourself

\item Check if important corner cases are missing
  
\end{itemize}
  
\end{slide}

\item What happens if \texttt{values} is empty?

\begin{slide}{Context Management}

\begin{itemize}

\item We mentioned that an agent's context memory is limited

  \begin{itemize}

    \item Every irrelevant piece of information creates noise
    
  \end{itemize}
    
\item Implementing code, an agent has to consider a lot:

  \begin{itemize}
    
  \item Specification

  \item Source code and its structure

  \item Tests

  \item Documentation
    
  \item Previous conversations

  \item Tool output

  \item Error messages
    
  \end{itemize}

\item Not all of this should be included in every interaction
  
\end{itemize}
  
\end{slide}



\begin{slide}{Context Management (2)}

\begin{itemize}

\item Provide the context needed for the current decisions

  \begin{itemize}
    
  \item Current subtask

  \item Relevant parts of the specification

  \item Relevant code files

  \item Relevant acceptance criteria
    
  \end{itemize}

\end{itemize}

\begin{slide}{When the Agent Gets Stuck}

\begin{itemize}

\item You might go through the implementation loop several times unsuccessfully

\item If this happens, it's time to revisit certain aspects

  \begin{itemize}
    
  \item Was the subtask too large?

  \item Did you review the code thoroughly enough?

  \item Are the tests wrong?

  \item Did the agent misunderstand the structure?

  \item Is the specification too ambiguous?
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Code Repositories}

\begin{itemize}

\item Code repositories, such as Git, store development snapshots you can go
  back to

\item For the moment, we recommend not to give an agent direct access to the
  repository

  \begin{itemize}
  
  \item Keep control by manually committing code

  \end{itemize}

\item Commit working states that are meaningful, i.e., you have successfully
  completed an intermediate step

\item If an agent messes up, you can go back to that state
  
\end{itemize}
  
\end{slide}



\begin{slide}{Summary}

\begin{itemize}

\item Generating code is only a part of the workflow

\item Also involves determining subtasks, planning, verification, reviewing, and
  debugging

\item Usually, you have to go through several iterations
  
\item An agent isn't replacing the development process

\item It is accelerating it

\end{itemize}

\begin{slide}{Testing}

\begin{quote}
\emph{``Beware of bugs in the above code; I have only proved it correct, not tested it.''}
\end{quote}
\hfill Donald Knuth % https://cs.stanford.edu/~knuth/faq.html)

\begin{itemize}

\item Testing is making sure our code does what we intend

\item For the purposes of this class, we focus on \textit{unit testing} \\
  (\url{https://en.wikipedia.org/wiki/Unit_testing})

  \begin{itemize}

  \item Basic and most important building block of most testing strategies

  \end{itemize}
    
\end{itemize}

\end{slide}



\begin{slide}{Example Test}

\begin{itemize}
  
\item A unit test verifies the correct operation of a small piece of code, often a single function.

\end{itemize}

\begin{tiny}
\begin{verbatim}
import pytest  # Import Python's unit testing framework
from addressverifier import AddressVerifier 
    # Import the module and class that we want to test

def testValidSwissAddress():
    # Call verifier with an address that should pass verification
    result = AddressVerifier().verify( 
         street="Rämistrasse 71", city="Zürich", canton="ZH",                  
         postalCode="8006", country="CH"              
     )                                 
     assert result.isValid  
         # "assert" makes the test fail when the statement is false
     assert result.errors == [] 
\end{verbatim}
\end{tiny}
  
\end{slide}



\begin{slide}{Another Test}

\begin{itemize}
  
\item Code that accepts all addresses as valid would pass the test on the previous slide

\item We can add a test for an address that should fail:

\end{itemize}

\begin{tiny}
\begin{verbatim}
import pytest  # Import Python's unit testing framework
from addressverifier import AddressVerifier 
    # Import the module and class that we want to test
                  
def testInValidSwissAddress():
    # Call verifier with an address that should fail verification. 
    result = AddressVerifier().verify(
        street="Rämistrasse 71", city="Zürich", canton="HH",  
        postalCode="80060", country="CH"
    )                                                              
    assert not result.isValid  
        # "assert" makes the test fail when the statement is false
    assert len(result.errors) == 2 # Expect to find two errors
    assert "NoSuchCanton" in result.errors  # non-existent canton
    assert "BadPostCode" in result.errors   # Invalid postcode
\end{verbatim}
\end{tiny}
  
\end{slide}



\begin{slide}{Test-driven development (TDD)}

  \begin{itemize}
    
  \item Writing the tests first can be useful because it makes you think about how your interface will be called:
    
    \begin{itemize}
    \item what data will a caller provide?
    \item which return values will make sense to them?
    \item which error codes will be useful?
    \end{itemize}
    
  \item Encourages you to test your \textit{interface} rather than your \textit{implementation}.
    
  \end{itemize}
  
\end{slide}



\begin{slide}{TDD Process}
  
  \begin{itemize}
    
  \item Work on one feature at a time
    
  \item A feature can be
    
    \begin{itemize}
      
    \item an interface method
      
    \item  or even one behavior of an interface method
      
    \item  For example, "Postcodes can be specified as XXXX or CH-XXXX"
      
    \end{itemize}
    
  \item Write tests for that one feature.
  \item Run the tests and verify that they fail.
  \item Fix the code until all the tests pass.
    
  \end{itemize}
  
\end{slide}



\begin{slide}{TDD Process (2)}
  
  \begin{itemize}
    
  \item Reviewing tests is easier than reviewing code!

  \item You can ask the coding agent to write the tests first
    
  \item You review the tests, and only then let the agent modify the code
    
  \end{itemize}
  

\end{slide}






\begin{slide}{Test coverage}

\begin{itemize}

\item How much testing is enough?

\item \textit{Test coverage} measures how many of your project's lines of code
  get executed by tests
  
\item Gives you a rough idea how much of your functionality is getting tested.

\item Between 70\% and 80\% line coverage is a good goal

  \begin{itemize}

  \item Higher coverage has diminishing returns

  \end{itemize}
  
  \item Ask the agent to check and maintain test coverage

  \item This is included in our sample \textit{AGENTS.md} file

\end{itemize}

\end{slide}



\begin{slide}{What Do Good Tests Look Like?}

\begin{itemize}
  
\item Good tests give you confidence:

  \begin{itemize}
  \item Run automatically
  \item Complete quickly
  \item Let you catch mistakes early
  \end{itemize}

\item Good tests

  \begin{itemize}
  \item focus on a single feature
  \item test the \textit{interface}, not the \textit{implementation}
  \item run quickly and without external dependencies, i.e.,

    \begin{itemize}
      
      \item no access to the internet or production data stores

    \end{itemize}
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{What Do Bad Tests Look Like?}

\begin{itemize}
  
\item  Bad tests fail a lot 

  \begin{itemize}
    
  \item You end up fixing the tests rather than the code

  \end{itemize}

  \item This mainly happens for two reasons:
    
    \begin{itemize}
      
    \item \textit{brittle} tests are tied to the \textit{implementation}
      rather than the \textit{interface}
      
      \begin{itemize}
        
      \item Need to be changed even for small code changes
        
      \end{itemize}
      
    \item \textit{flaky} tests depend on behavior or state outside of the
      scope of the system under test

      \begin{itemize}
        
      \item For example, an external data store
        
      \item Tend to be slow and to fail randomly
        
      \end{itemize}
      
    \end{itemize}
    
\end{itemize}

\end{slide}



\begin{slide}{External Dependencies}

\begin{itemize}
  
\item What happens if you have external dependencies?

  \begin{itemize}

  \item For example, you test code that accesses a database

  \end{itemize}

\item Mocks are your friend: \\
 \url{https://pytest-mock.readthedocs.io/en/latest/}

\end{itemize}

\end{slide}




\begin{slide}{Tests Written By Coding Agents}

\begin{itemize}
  
\item Absent careful prompting or relevant \textit{skills},

  \begin{itemize}

  \item LLMs often write tests that are both brittle and flaky

  \end{itemize}

\item Not a big problem for small, short projects

\item Becomes annoying when using and extending the code

\end{itemize}

\vspace*{.5cm}

\begin{itemize}
  
\item Takeaway:

  \begin{itemize}
    
  \item Put good testing practices into the context
    
  \item Review the tests to make sure they stay useful
    
  \end{itemize}
  
\end{itemize}

\end{slide}




\begin{slide}{Summary: TDD}

\begin{itemize}
  
\item Good tests are a recipe for useful software

\item They ensure that

  \begin{itemize}
  \item new code satisfies new requirements
  \item modifications to existing code don't break existing features
  \end{itemize}

\item Tests are easiest to write for well-structured code with clear interfaces
  
  \begin{itemize}

  \item Difficulties in creating small independent tests can point to a
    problem in the interface design

  \end{itemize}

\end{itemize}
  
\end{slide}

\begin{slide}{Debugging}

\begin{itemize}

\item Eventually, your code will contain a bug

  \begin{itemize}
    
  \item That means, it doesn't produce the expected output
    
  \end{itemize}

\item Proper reaction is not just telling the agent: fix this

\item It should be resolved in the following way:

  \begin{itemize}
    
  \item Reproduce the failure reliably (what)

  \item Then, investigate the cause (why)

  \item Finally, fix the problem
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Example}

\begin{itemize}

\item Let's go back to the example for calculating averages

\begin{verbatim}
calculate_average(values):
     return sum(values) / len(values)
\end{verbatim}

\item Your program just crashed, outputting

\begin{verbatim}
File "...", line x, in calculate_average
ZeroDivisionError: division by zero
\end{verbatim}
  
\item Give this error message to the agent and ask it

  \begin{itemize}
    
  \item to investigate what is going on and

  \item to hypothesize why it is happening
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Investigate}

\begin{itemize}

\item Have a look at the agent's answer

  \begin{itemize}
    
  \item Does it explain what is happening?
    
  \end{itemize}

\item Clearly, a division by zero triggers the error

  \begin{itemize}
    
  \item But why is \texttt{values} empty?
    
  \end{itemize}

\item Can this error be reproduced with other inputs?

  \begin{itemize}
    
  \item This further evaluation can be supported by the agent again
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Example}

\begin{itemize}

\item The agent may come back with the following answer

  \begin{itemize}
    
  \item The input file did not pass the validation

  \item This resulted in \texttt{values} not being properly initialized
    
  \end{itemize}

\item This can be tested by using corrupt input files that cannot be validated
  
\end{itemize}
  
\end{slide}



\begin{slide}{Preparing Modification}

\begin{itemize}

\item Once you're happy with the diagnosis, you can ask the agent to prepare
  the modification

\item Review the modification

\item If you're satisfied, ask the agent to modify the code

\item Also test the code!

\end{itemize}
  
\end{slide}


\begin{slide}{Testing}

\begin{itemize}

\item Ideally, the test for the modification is generated before the
  modification itself

  \begin{itemize}
    
  \item Clearly, it will fail without the fix

  \item Goal is to make it pass
    
  \end{itemize}

\item Also run the other tests to check that nothing else was broken

  \begin{itemize}
    
  \item This is called \emph{regression testing}
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}

\begin{slide}{Refactoring}

\begin{itemize}

\item There may be another reason to modify code

  \begin{itemize}
    
  \item The code gives correct results

  \item But it is messy, ugly, and hard to understand
    
  \end{itemize}

\item What do we mean by this?

  \begin{itemize}
    
  \item One large function doing all the work

  \item Duplicated logic

  \item Unclear and confusing naming

  \item Deeply nested conditionals

  \item Unrelated responsibilities in one module

  \item Weak abstraction boundaries
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}


\begin{slide}{Refactoring (2)}

\begin{itemize}

\item \emph{Refactoring} is about giving code a better structure
  \textbf{without} changing its behavior

  \begin{itemize}
    
  \item Debugging changes behavior and structure
    
  \end{itemize}
  
\item Testing is also very important when refactoring

  \begin{itemize}
    
  \item Don't refactor code that isn't covered by tests
    
  \end{itemize}

\item Typical workflow of refactoring
  
  \begin{itemize}
    
  \item Understand behavior

  \item Run existing tests

  \item Identify missing tests and add tests if necessary

  \item Refactor

  \item Run tests again

  \item Evaluate
    
  \end{itemize}

\end{itemize}
  
\end{slide}


\begin{slide}{Agentic Refactoring}

\begin{itemize}

\item Again, it's not enough to just say: refactor this

\item Be specific in your instructions

\item For example, you want to refactor the module \texttt{Parser}, then you
  may want to give these instructions:

  \begin{itemize}
    
  \item Refactor \texttt{Parser} to separate parsing from validation

  \item Preserve the API and the observable behavior

  \item Do not change the file format or error semantics

  \item Run the tests after each significant change
    
  \end{itemize}

\item Looks similar to specifications and constraints
  
\end{itemize}
  
\end{slide}


\begin{slide}{Agentic Refactoring (2)}

\begin{itemize}

\item After agent finishes refactoring, verify the results
  
  \begin{itemize}
    
  \item Run all available tests

  \item Check the differences in the code

  \item Manually check behavior of critical parts
    
  \end{itemize}
    
\item The effort you have to make depends on modifications

  \begin{itemize}
    
  \item Less for a few variable name changes

  \item More for a rewrite of a core component
    
  \end{itemize}

\end{itemize}
  
\end{slide}


\begin{slide}{Summary}

\begin{itemize}

\item Debugging/refactoring follows similar workflow as agentic implementation

  \begin{itemize}
    
  \item Do not let the agent do everything on its own

  \item Embed the work into a feedback loop
    
  \end{itemize}

\end{itemize}
  
\end{slide}
