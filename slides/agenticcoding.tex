\begin{slide}{Things are Definitely Changing}

\begin{itemize}

\begin{slide}{Basic Terminology}

\begin{itemize}

\item Coding with AI covers a whole spectrum
 
\begin{itemize}

\item Vibe coding: prompt and hope for the best

\item Agentic coding: a systematic approach that still utilizes software
  development principles

\end{itemize}

\end{itemize}

\begin{slide}{Vibe Coding}

\begin{itemize}

\item Vibe coding typically looks like the following:

\begin{itemize}

\item Write a prompt, e.g. ``Build an app that does X.''

\item LLM generates some code

\item User tries it out, doesn't quite work

\item User writes another prompt requesting some changes

\item LLM changes code

\item Wash, rinse, repeat

\end{itemize}
  

\end{itemize}
  
\end{slide}



\begin{slide}{Agentic Coding}

\begin{itemize}

\item This is not about writing simple prompts

\item Gives an LLM specific software development tasks in a systematic way,
  such as:

\begin{itemize}

\item Formulate goal, e.g., in form of a specification

\item Devise a plan, break up general task into subtasks

\item Generate code

\item Validate code, e.g., by running tests

\item If necessary, revise implementation (or even planning)

\end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Vibe-Coding vs. Agentic Coding}

\begin{itemize}

\item That doesn't necessarily mean that vibe coding is bad and agentic coding
  is good

\item Vibe coding:

  \begin{itemize}
    
  \item makes sense for rapid prototyping
    
  \item is for quickly trying out things
    
  \end{itemize}
    
\item Agentic coding

  \begin{itemize}
    
  \item is a thorough process
    
  \item creates reliable code
    
  \end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{What Can Go Wrong?}

\begin{itemize}

\item AI gets stuck in infinite loops

\item Deliver incorrect solutions confidently

\item Cheat: optimize for validation such as benchmarks
  
\item Implements what you said, not what you meant

\begin{itemize}

\item General problem, existed before AI

\end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Summary}

\begin{itemize}

\item Then: translate ideas into code (programming)

\item Now: translate ideas into prompts (vibe-coding)

\item Then: (systematically) applying principles and methods to create
  reliable software (software engineering)

\item Now: give an AI (software-engineering) goals and constraints to create
  software (agentic coding)

\item Important question: how much of the software-engineering process can be
  delegated?
  
  
\end{itemize}
  
\end{slide}

\begin{slide}{OpenCode}

\begin{itemize}

\item OpenCode is an open-source coding tool

\item Connects LLMs to development tools

\item Model-agnostic: can run (almost) every model you want

\item By default, stores code locally

\end{itemize}

\begin{center}
\includegraphics[width=7cm]{pics/opencode.eps}

\begin{slide}{Interaction with Files}

\begin{itemize}

\item OpenCode is not an editor:

\begin{itemize}

\item You can use any editor you want (VS Code, Emacs, IntelliJ) to look at
  the files

\item OpenCode executes commands in a terminal

\end{itemize}

\item With these commands it can manipulate files and use other tools

\begin{itemize}

\item This has direct implications on security

\end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Repositories}

\begin{itemize}

\item A repository is where a version control system (VCS) stores its data

\item A VCS tracks and manages changes to files

\begin{itemize}

\item Heavily used in managing source code

\end{itemize}

\item Allows to revert to a previous state

\item Facilitates collaboration 

\end{itemize}
  
\end{slide}



\begin{slide}{Model Context Protocol (MCP)}

\begin{itemize}

\item We just mention it for sake of completeness

\item It is an open standard specifying how LLMs share data with external
  tools

\item MCP offers a standardized interface for

  \begin{itemize}

  \item reading files

  \item executing functions

  \item handling prompts

  \end{itemize}

\end{itemize}

\begin{slide}{Introduction}

\begin{itemize}

\item The aim is not to give a detailed technical description of LLMs (and the
  agents utilizing them)

\begin{itemize}

\item You don't need to build an LLM or agent,

\item but to understand how they react to your input

\end{itemize}

\item In a nutshell, an LLM is autocomplete on steroids

\begin{itemize}

\item It doesn't look up an answer

\item It generates its response incrementally, depending on the context and
  the data it was trained on

\end{itemize}
  
\end{itemize}
  
\end{slide}



\begin{slide}{Autocomplete vs. LLM}

\begin{itemize}

\item If you type a message on your phone, it tries to predict how the message
  continues

\begin{itemize}
  
\item Uses a dictionary and probabilities for continuations

\end{itemize}
  
\item An LLM works at a different scale

\begin{itemize}

\item Instead of a dictionary, uses a neural network with billions or
  trillions of parameters

\item Utilizes a much larger context (thousands of words)

\item Depending on the setting, it may not always return the most probable answer
  
\end{itemize}

\end{itemize}
  
\end{slide}



\begin{slide}{Tokens}

\begin{itemize}

\item An LLM doesn't work with words, uses tokens instead

\item We only give a brief introduction to tokens

\item What do tokens look like?
  
\begin{itemize}

\item (Short) words, e.g. house

\item Parts of words, e.g. un con stitu tion al

\item Punctuation, whitespace, emojis
  
\end{itemize}

\item Tokens are used

\begin{itemize}
  
\item to avoid vocabulary explosion
\item identify new words
\item describe concepts independent of language

\end{itemize}

\end{itemize}
  
\end{slide}




\begin{slide}{Generating an Answer}

\begin{itemize}

\item Context: current prompt and previous input/output

\item An LLM then generates a plausible continuation: \\
context $\rightarrow$ next token $\rightarrow$ next token $\rightarrow$ next token

\item A generated token is added to the context

\item The \emph{context window} plays a crucial role
  
\end{itemize}

\vspace*{-.3cm}
\begin{center}
\includegraphics[height=4.5cm]{pics/contextwindowparadox.eps}
\end{center}


\end{slide}




\begin{slide}{Context Window}

\begin{itemize}

\item Process is driven by the content of the context window

  \begin{itemize}
  
  \item This window is not infinitely large
    
  \item Higher recall at edges (beginning/end)

\end{itemize}
  
\item Some similarity to our working memory

  \begin{itemize}

  \item Can hold seven chunks of information (+/-2)

  \item Serial position effect (easier to remember start/end)
    
  \end{itemize}

\end{itemize}

\vspace*{.5cm}

\begin{itemize}
  
\item Takeaway: if we want good results, we have to provide the right context
  
\end{itemize}
  
\end{slide}




\begin{slide}{From Chatbot to Agent}

\begin{itemize}

\item We don't want to use the LLM in the following way: \\
  prompt $\rightarrow$ answer

\item First of all, there's an issue with reliability

  \begin{itemize}

  \item LLMs can be confidently incorrect
  
  \end{itemize}

\item Given a prompt (and all their learned patterns), an LLM gives plausible
  answers

  \begin{itemize}

  \item LLMs do not know what the outside world looks like
  
  \end{itemize}

\item We want evidence for correctness

  \begin{itemize}

  \item Idea: give LLMs access to tools for checking
  
  \end{itemize}
  
\end{itemize}
  
\end{slide}

\begin{slide}{From Chatbot to Agent (3)}

\begin{itemize}

\item In the context of coding, we provide tools such as

  \begin{itemize}
    
  \item Requirement/specification documents
    
  \item Code files
    
  \item Tests
    
  \item Current repository and history
    
  \item External documentation
    
  \end{itemize}

\item In agentic coding, the LLM itself is not the agent

  \begin{itemize}

  \item It's the system around it implementing the loop
    
  \end{itemize}
  
\end{itemize}
  
\end{slide}
